The Core Challenge

Why Collaborative Editing is Hard

⚠️

Race Conditions

When User A and User B type at position 10 concurrently, network latency causes edits to arrive out of order.

🚫

Last-Write-Wins Fails

Traditional databases pick whichever edit arrived last and overwrite the other, causing permanent data loss.

🌐

Unreliable Networks

Network partitions and high latency break traditional sync models. Offline edits must reconcile smoothly upon reconnect.

The Engine Architecture

Conflict-Free Mathematical Convergence

🧬 Yjs YATA Algorithm

Every character insertion is assigned a unique client ID and logical Lamport clock. Characters are linked as items in a doubly linked list, guaranteeing non-interleaving text merging without locks or master servers.

⚡ Binary WebSocket Synchronization

Mutations are serialized into ultra-compact binary byte buffers using lib0 variable-length encoding (average packet size < 80 bytes), achieving sub-10ms propagation.

✨ Result: Zero race conditions, mathematical convergence, and zero data loss.
Fault Tolerance & Resilience

Dual-Tier Offline Persistence

📱 Tier 1: Client-Side IndexedDB

Integrated y-indexeddb saves every keystroke locally in the browser. Users can edit while completely disconnected, close the tab, and resume offline without data loss.

💾 Tier 2: Server-Side Disk Snapshots

The Node.js collaboration server captures binary CRDT state updates into persistent .yjs files in dbDir/. Documents survive complete backend reboots.

🔄 Reconnection Protocol: Exchanges state vectors, transmits missing delta updates only, and reconciles state automatically.
